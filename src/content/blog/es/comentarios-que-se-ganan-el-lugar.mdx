Hay un tipo particular de comentario que aparece en todas las bases de código que heredé:

```python
# incrementar el contador
counter += 1
```

No está mal. Simplemente le está cobrando al lector por información que ya tenía.
Multiplicalo por unos miles de líneas y tenés una base de código donde los comentarios son
ruido, lo que significa que los tres realmente importantes se leen por arriba junto con
todo lo demás.

## El test que uso

Antes de escribir un comentario me pregunto si el código podría decirle esto al lector por
sí solo. Si puede, el comentario es un síntoma y lo que hay que cambiar es el código.

```js
if (u.s === 2 && Date.now() - u.t > 604800000) { ... }
```

El instinto es explicar esa línea. La mejor jugada es eliminar la necesidad:

```js
const isDormantSubscriber =
  user.status === Status.Subscribed && daysSince(user.lastSeen) > 7;

if (isDormantSubscriber) { ... }
```

Ningún comentario sobrevive a esa reescritura, porque ya no queda nada que explicar.

<Callout variant="note" title="La versión de una línea">
  Si un comentario explica qué hace el código, reescribí el código. Si explica por qué el
  código tiene esta forma, dejalo, porque esa información no existe en ningún otro lado.
</Callout>

## Qué sobrevive al test

Los comentarios se ganan su lugar cuando llevan contexto que el código físicamente no puede:

```js
await sleep(250);
```

¿Por qué 250? Nada en la base de código puede responder eso. La API de upstream limita a
cuatro requests por segundo y devuelve un 200 con el body vacío en lugar de un 429 cuando
te pasás, algo que llevó una tarde descubrir. Eso va en un comentario, porque si no la
próxima persona va a bajar el número y va a reintroducir un bug que no parece un bug.

Lo mismo vale para un workaround atado a un bug de upstream, una fórmula sacada de un paper
específico, o una desviación deliberada de una convención que se usa en todo el resto del
repo. En cada caso la información vive fuera del código, así que el código no puede
expresarla.

## Por qué este sitio no tiene ninguno

Este portfolio está escrito sin un solo comentario de código, lo que suena a truco y en
parte es una restricción que me puse para ver a qué me obligaba.

Sobre todo me obligó a mejores nombres. Cuando no podés anotar `pickForLocale`, te enterás
rápido de si el nombre de la función está haciendo su trabajo. Las dos o tres decisiones
genuinamente sorprendentes, como por qué el selector de idioma recibe URLs explícitas en
lugar de intercambiar un segmento de la ruta, se mudaron al README, donde alguien que
evalúa el proyecto realmente se las va a cruzar.

Esa mudanza es el argumento de verdad. Un comentario llega a quien abre ese archivo. Un
README llega a quien abre el proyecto. Para una decisión que le da forma a toda la
arquitectura, el segundo público es el correcto.

No aplicaría esta regla en la base de código de un equipo grande sin la válvula de escape
de más arriba. Pero como función forzante en un proyecto de este tamaño, se ganó su lugar.
