There is a particular kind of comment that shows up in every codebase I have inherited:

```python
# increment the counter
counter += 1
```

It is not wrong. It is just billing the reader for information they already had. Multiply
it by a few thousand lines and you get a codebase where comments are noise, which means
the three genuinely important ones get skimmed along with everything else.

## The test I use

Before writing a comment I ask whether the code could tell this to the reader itself. If
it could, the comment is a symptom and the code should change instead.

```js
if (u.s === 2 && Date.now() - u.t > 604800000) { ... }
```

The instinct is to explain that line. The better move is to delete the need:

```js
const isDormantSubscriber =
  user.status === Status.Subscribed && daysSince(user.lastSeen) > 7;

if (isDormantSubscriber) { ... }
```

No comment survives that rewrite, because there is nothing left to explain.

<Callout variant="note" title="The one-line version">
  If a comment explains what the code does, rewrite the code. If it explains why the code is shaped
  this way, keep it, because that information exists nowhere else.
</Callout>

## What survives the test

Comments earn their keep when they carry context the code physically cannot:

```js
await sleep(250);
```

Why 250? Nothing in the codebase can answer that. The upstream API rate-limits at four
requests per second and returns a 200 with an empty body instead of a 429 when you exceed
it, which took an afternoon to discover. That belongs in a comment, because the next
person will otherwise tune the number down and reintroduce a bug that does not look like
one.

The same goes for a workaround pinned to an upstream bug, a formula from a specific paper,
or a deliberate deviation from a convention used everywhere else in the repo. In each case
the information lives outside the code, so the code cannot express it.

## Why this site has none

This portfolio is written without a single code comment, which sounds like a stunt and is
partly a constraint I set to see what it would force.

Mostly it forced better names. When you cannot annotate `pickForLocale`, you find out
quickly whether the function name is doing its job. The couple of genuinely surprising
decisions, like why the language switcher takes explicit URLs instead of swapping a path
segment, moved into the README where someone evaluating the project will actually
encounter them.

That relocation is the real argument. A comment reaches whoever opens that file. A README
reaches whoever opens the project. For a decision that shapes the whole architecture, the
second audience is the right one.

I would not run this rule on a large team codebase without the escape hatch above. But as
a forcing function on a project this size, it earned its keep.
